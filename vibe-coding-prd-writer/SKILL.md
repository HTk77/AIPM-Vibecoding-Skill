# Vibe Coding PRD Writer

## 0. 是什么 / 谁用 / 与传统 PRD 的差别

**用户画像:** 产品经理(可能不会写代码),用 AI 编程工具(Claude Code / Cursor / Lovable / Bolt / Windsurf 等)指挥 AI 完成产品。

**输出对象:** 不是给人开发评审的传统 PRD,**是给 AI 直接消费、能照着干活的执行文档**。

**核心差别:**

| 维度 | 传统 PRD(给人看) | Vibe PRD(给 AI 看) |
|------|------------------|-------------------|
| 优先描述 | "做什么" | **"做什么 + 不做什么 + 怎么验证做对了"** |
| 模糊度 | 可模糊,人会推理补全 | 必须精确,AI 模糊执行 = 模糊代码 |
| 验收 | 后置文档 | 每个功能内嵌 |
| 边界 | 隐含 | 显式声明 |
| 设计 | 链接 Figma 即可 | 必须有具体 token 或链接到原型源码 |
| 文档结构 | 大块叙述 | **模块化、解耦、可独立增删** |
| 示例语言 | "用户体验流畅" | "首字节 < 5 秒,用户能看到流式光标" |

**核心理念:** 模糊 → AI 自由发挥 → 不是你想要的产品。**Vibe PRD 用结构换确定性。**

---

## 1. 第一件事:判断"AI 产品" vs "功能产品"

参考行业共识(《AI 应用 = 传统功能产品 + AI 能力》),AI 产品 PRD 比功能产品多 5 项必写内容,**判断错会导致 PRD 严重不合格**。

### 1.1 怎么判断

只要满足**任一条**,即视为 AI 产品:
- 底层调用 LLM(GPT / Claude / DeepSeek / Qwen / 等)
- 涉及生成式输出(文本 / 图像 / 音视频)
- 涉及 RAG / Agent / 工具调用 / 多模态
- 涉及训练 / 推理 / 评测

### 1.2 AI 产品 vs 功能产品的差异速查

| 章节 | 功能产品 | AI 产品(额外要求) |
|------|---------|-------------------|
| 项目身份卡 | 标准字段 | **+ AI 三要素公式自检**(见 §3.1) |
| 功能契约 | 标准字段 | **+ 评测指标(准确率/召回率/...)** |
| 边界声明 | 兜底策略 | **+ 合规 / 法务风险评估**(参考行业:B 站智能封面合规踢出局案例) |
| 设计技术契约 | 技术栈 | **+ 数据质量 / 算力延迟 / 端侧vs云端 + 评测体系** |
| 撰写流程 | 直接写 | **+ POC 验证前置**(参考行业 AI 流程:POC 失败 → 暂缓) |

### 1.3 AI 产品 PRD 的额外章节

详见 [`references/ai-product-extras.md`](./references/ai-product-extras.md):
- AI 三要素公式(用户痛点 × 数据可获得性 × 算法可实现性)
- 评测指标体系
- 数据采集三渠道(用户原声 / 数据埋点 / 效果评测)
- POC 验证流程
- 合规风险清单

> **AI 项目时本 skill 必读 ai-product-extras.md;功能产品可跳过。**

## 2. ⭐ 撰写流程:4 阶段 + 3 个用户确认点(核心)

> **关键原则:不要拿到模糊需求就开始写 PRD。中间必须有 3 次显式确认,把 AI 的"自说自话"变成"和用户对齐过"。**

```
阶段 1: 输入对齐
  ├─ 列出"上一步"必须有的资料清单
  ├─ 检查每项是否齐全,缺则停止,要求用户补
  └─ ✋ 用户确认 #1: "输入信息我都给齐了吗?"
        ↓
阶段 2: 产品架构设计
  ├─ 产出 3 项(AI 项目额外加第 4 项):
  │   ① 产品形态(单页/多页/对话/工具流/多端)
  │   ② 核心用户流(用户从打开到完成主任务的路径)
  │   ③ 模块拆分(几个模块,模块间关系)
  │   ④ AI 介入点(AI 项目专属:哪里用 LLM,做什么任务)
  └─ ✋ 用户确认 #2: "架构是不是你想的样子?"
        ↓
阶段 3: PRD 撰写(5 必写模块)
  ├─ §3 中的 5 个模块按顺序填
  └─ AI 项目同步启用选填模块(§4)
        ↓
阶段 4: 二次确认 Walkthrough
  ├─ 用 walkthrough 方式逐模块过一遍
  ├─ 验收清单逐条让用户确认能跑通
  └─ ✋ 用户确认 #3: "PRD 我读完没歧义"
        ↓
       完成,交付给 AI 编程工具
```

### 2.1 阶段 1:输入对齐(必读 + 必问)

**输入资料清单**(根据情况勾选):
- [ ] 用户访谈记录 / 用户故事
- [ ] 竞品调研 / 市场分析
- [ ] 想法描述 / 业务方需求口述
- [ ] 已有的 BRD / MRD(若有)
- [ ] 已有的设计原型(若有,链接到文件路径)
- [ ] 资源约束(预算 / 人力 / 时间)
- [ ] 平台目标(Web / iOS / 小程序 / Android / 桌面)

**确认 #1 话术示例:**
> "在我开始写 PRD 之前,我需要确认你已经给齐这些信息:
> ① 目标用户画像 — [当前情况]
> ② 核心场景 / 用户故事 — [当前情况]
> ③ 平台目标 — [当前情况]
> ④ 资源约束 — [当前情况]
> 缺的 [列出] 你能补吗?如果暂时不能,我会在 PRD 里标 TBD。"

### 2.2 阶段 2:产品架构设计(独立环节,不和 PRD 一起写)

按顺序产出 3+1 项:

**① 产品形态**
- 单页 / 多页 / 单对话 / 多对话 / 工具流 / 多端协同 / Agent 编排
- 一句话讲清

**② 核心用户流**
- 用户从打开产品到完成主任务的步骤(用 → 箭头表示)
- 例:`打开 → 输入口令 → 选话题 → 提问 → 看 Agent 回复 → 追问 / 切换 / 结束`

**③ 模块拆分**
- 列出 3-7 个一级模块,标注模块间关系
- 例:`认证模块 → 聊天主区 ← 历史侧栏 ← 设置面板`

**④ AI 介入点**(仅 AI 项目)
- 哪里用 LLM,做什么任务,输入输出格式
- 是否需要 RAG / 工具调用 / 多步推理

**确认 #2 话术示例:**
> "我把架构设计完了,你看一下:
> - 产品形态:[X]
> - 用户流:[X → Y → Z]
> - 模块拆分:[A / B / C / D]
> - AI 介入点:[功能 X 用 LLM 做 Y]
>
> 任何一项不是你想的,告诉我,改对了再写 PRD。"

### 2.3 阶段 3:PRD 撰写

按 §3 的 5 必写模块依次填。AI 项目同步参考 §4 启用选填。

### 2.4 阶段 4:二次确认 Walkthrough

写完 PRD,**不要直接交付**,而是:

1. **逐模块朗读式确认**:"项目身份卡:产品名 X,目标用户 Y,你确认吗?"
2. **验收清单逐条问**:"验收第 1 条:用户输错口令 → 显示红色提示。这是你期望的吗?"
3. **请用户找 1 处歧义**:"如果你读这份 PRD 有任何'看不懂'或'模糊'的地方,告诉我,我改"

**确认 #3 话术示例:**
> "PRD v0.1 写完了。我用 walkthrough 方式带你过一遍:
> - 项目身份卡:[摘要]
> - 5 个 P0 功能:[每条的核心句]
> - 边界声明:[列不做的 3 条]
> - 设计技术契约:[关键决策]
> - 验收清单:[随机抽 2 条详读]
>
> 你读完后告诉我:① 哪里有歧义 ② 哪里不是你想的 ③ 哪里要补。
> 都没问题,我们就锁定 v1.0。"

## 3. 5 个必写模块

每份 Vibe PRD 必含以下 5 模块,顺序固定。少一个不算合格。

> **填空模板**详见 [`references/templates.md`](./references/templates.md)
> **跨行业微示例**详见 [`references/micro-examples.md`](./references/micro-examples.md)

### 模块 1️⃣:项目身份卡 (Identity Card)

**定义:** 一段 30 秒内能让任何 AI 上手的"项目自我介绍"。

**为什么必须有:** 不同 AI 对话窗口、不同人协作,首先要对齐"这是个什么东西"。模糊的身份卡 → AI 抽风。

**必填字段:**
- 产品名(中英)
- 一句话定位(谁的什么工具,解决什么问题)
- 目标平台(Web / iOS / Android / 小程序 / 桌面 / Agent)
- 目标用户(画像 + 使用场景 + 频率)
- 核心价值主张(≤ 3 条,差异化)
- 项目类型(B 端 / C 端 / AI 产品 / 工具 / 内容 / 平台)
- 项目规模(个人 / 小团队 / 战略级)

**AI 项目额外字段(项目级 AI 三要素自检):**
| 字段 | 自答 |
|------|------|
| 用户痛点强度 | 1-10 分 + 一句话场景描述 |
| 数据可获得性 | 数据从哪来 + 是否独家 + 标注成本 |
| 算法可实现性 | 现有 LLM 能不能做 + 备选方案 |

> 三要素任一项 < 3 分,**强烈建议先 POC 再写 PRD**(详见 §4 选填模块)。

### 模块 2️⃣:功能契约 (Feature Contract)

**定义:** 每个功能都是一份契约,白纸黑字写清做什么、什么时候触发、输入输出、怎么算做对了、优先级。

**为什么必须有:** AI 写代码本质是按契约执行。契约模糊 = 代码胡来。优先级缺失 = AI 把所有功能都做成 P0。

**每条功能必填:**
- ID(F1, F2, F3...)
- 名称
- **用户故事**(标准句式:"作为 [谁],我想要 [做什么],以便 [达成什么目的]")
- 描述(一句话)
- 触发条件
- 输入(用户/系统提供什么)
- 输出(返回什么 / 界面变化)
- 边界情况(空 / 异常 / 超长 / 网络断 / 重复操作)
- 验收标准(3-5 条可勾选)
- 优先级(P0 / P1 / P2)

**AI 项目额外字段(功能级 AI 三要素自检 + 评测):**
- AI 三要素回答(本功能维度)
- 评测指标(准确率 / 召回率 / 响应时间 / 满意度,选 1-3 条)
- 数据采集渠道(用户原声 / 数据埋点 / 效果评测,至少 1 条)

### 模块 3️⃣:边界声明 (Scope Boundary)

**定义:** 显式列出**不做什么**,以及做不到时怎么兜底。

**为什么必须有:** AI 倾向"贴心地多做一点",这是灾难。明示边界 = 砍掉 AI 自动加戏的入口。LLM/网络/外部依赖会失败,没有兜底就是隐性 bug。

**必填:**
- 不做的事(本版不做 / 永远不做,带原因)
- 取舍说明(为什么选 A 不选 B)
- 兜底策略(API 失败 / 超时 / 网络断 / 数据丢失 / 用户误操作)

**AI 项目额外字段:**
- 合规 / 法务风险评估(数据隐私 / 内容审核 / 版权 / 算法偏见 / 行业监管)
- 高风险点的应对方案(法务前置 / 内容过滤 / 模型微调 / 等)

> 参考行业警示案例:**B 站智能封面项目上线前一周被法务约谈砍掉**。AI 项目合规必须前置,不能等到上线前才补。

### 模块 4️⃣:设计与技术契约 (Design & Tech Contract)

**定义:** 锁定技术栈、设计风格、关键数据结构、API 协议。AI 不许再讨价还价。

**为什么必须有:** AI 有自己的偏好,不锁定就会按它的喜好选。一旦中途切换技术栈,代价巨大。

**必填:**
- 技术栈(语言 / 框架 / 库 / 部署平台,每条带版本和理由)
- 设计参考(具体的 design system 名 / prototype.html 路径 / 设计 token 列表)
- 数据 schema(关键数据结构,LocalStorage 字段 / API 请求响应 / 数据库表)
- API 协议(接口列表,带请求/响应 schema)
- 安全要求(API key 存哪、口令怎么校验、不许什么)

**AI 项目额外字段:**
- 模型选型(用什么 LLM / 什么版本 / 为什么)
- 数据质量评估(脏数据率 / 标注成本 / 训练集规模)
- 算力与延迟(端侧 vs 云端 / 单次请求延迟 / 并发能力)
- 评测体系(metric 定义 / 评测集 / 评测频率) — 详见 [`ai-product-extras.md`](./references/ai-product-extras.md)

### 模块 5️⃣:验收清单 (Acceptance Checklist)

**定义:** 端到端的可执行测试场景。逐条跑通 = MVP 完成。

**为什么必须有:** "做完了"必须可度量。AI 自评"我做完了"不算数。

**必填:**
- ≥ 5 条端到端测试场景
- 每条:用户视角具体操作 + 期望可观察结果
- 涵盖正常路径 + 至少 1 条异常路径
- 涵盖所有 P0 功能

**AI 项目额外字段:**
- 数据采集三渠道全覆盖:
  - 用户原声(用户主动反馈 / 评分入口在哪)
  - 数据埋点(关键行为埋点清单,带 metric 名)
  - 效果评测(评测集运行频率 + 通过率门槛)

## 4. 选填模块(按项目特征启用)

| 模块 | 何时必启 | 用途 |
|------|---------|------|
| **AI 协作元数据(CLAUDE.md 提示)** | 任何要长期迭代的项目 | 提醒接手 AI 怎么读、决策权分层、常见操作 SOP |
| **Agent 角色契约** | 涉及 LLM 角色扮演 / 多 Agent | 角色定义 + prompt 工程出处 + 失败模式 |
| **POC 验证记录** | AI 项目且 AI 三要素任一 < 3 分 | POC 目标 / 数据 / 评测结果 / 是否进入正式 PRD |
| **状态机** | 复杂状态流转(订单 / 表单流) | 显式画状态转移,杜绝 AI 自创状态 |
| **错误目录** | 用户可见错误较多 | error code → 用户文案 → 处理动作 |
| **数据飞轮** | 数据驱动型产品 | 输入数据 → 行为数据 → 模型 → 输出 闭环 |
| **运营计划** | C 端 / 商业产品 | 冷启动 / 留存 / 增长机制 |

## 5. 6 条写作铁律(每个模块都适用)

### 铁律 1:可勾选 > 描述
错:"用户体验要流畅"
对:"3 个 Agent 卡片同时开始流式输出,首字节 < 5 秒"

### 铁律 2:行为可观测 > 内部机制
错:"使用 SSE 实现流式"(放模块 4)
对:"用户感知到 Agent '正在打字' 的即时感"(放验收)

### 铁律 3:每个功能必有验收
不写验收的功能 = 没契约 = AI 可以随便解释做完了。

### 铁律 4:边界必须显式
"不做什么"和"做什么"等重要。AI 不会自动假设你不要某个功能。

### 铁律 5:设计/技术决策必须可追溯
"用 X 不用 Y" 必须有 1 句理由。否则 AI 会"看似优化"地换掉。

### 铁律 6:**字不如表,表不如图** ⭐(行业核心口诀)
- 能用列表别用段落
- 能用表格别用列表
- 能用流程图 / 架构图 / 状态图别用文字描述
- 数据 schema 必须用代码块,不能散文化
- 用户流必须画箭头,不能"先 X 然后 Y"

> 这条铁律来自实战经验:能用一张图说清楚的事,文字写 100 字 AI 都可能误读。

## 6. 输出格式(解耦设计)

PRD 必须解耦,**便于后续单模块增删改而不改全局**。

### 6.1 默认结构(单文件多 section,适合中小项目)

```
docs/PRD.md
├── # 项目名 — Vibe Coding PRD
├── ## 1. 项目身份卡
├── ## 2. 功能契约
│   ├── ### 2.1 F1 [name]
│   ├── ### 2.2 F2 [name]
│   └── ...
├── ## 3. 边界声明
├── ## 4. 设计与技术契约
├── ## 5. 验收清单
└── ## 6. 选填模块(若启用)
```

### 6.2 大型项目(模块拆文件)

```
docs/
├── PRD.md                    ← 索引主文件,只放概要 + 链接
└── prd/
    ├── 01-identity.md
    ├── 02-features.md
    ├── 03-boundary.md
    ├── 04-design-tech.md
    ├── 05-acceptance.md
    └── 06-optional/
        ├── ai-extras.md       ← AI 项目专属
        ├── poc-record.md      ← AI 项目 POC 记录
        └── ...
```

### 6.3 解耦三铁律

1. **每个模块必须有锚点 ID**,方便其他文档跨链引用
2. **每个 P0 功能独立成三级标题**,便于单独修改不影响其他功能
3. **设计 token / API / 数据 schema 用代码块包裹**,不要散落叙述里

## 8. 失败模式(常见坑)

| 失败示例 | 为什么是失败 | 怎么改 |
|---------|------------|------|
| "F1: 用户登录,提供良好的体验" | 没验收,"良好"不可观测 | 加可勾选项:"用户输错口令 → 显示红色提示" |
| "用什么前端框架由开发决定" | AI 没法决定,会自选 | 锁定:"Next.js 14" + 1 句理由 |
| "支持手机和电脑" | 模糊,AI 按它理解做 | 拆细:"<768px 单列;≥1024px 三列" |
| 验收写"测试通过即可" | 没具体场景 | 列具体动作:"用户输错口令 3 次仍能输入" |
| 没写边界声明 | AI 加戏 | 至少列 3 条"本版不做",每条带原因 |
| 设计写"简洁现代" | 太主观 | 链接到具体 design system + token 文件 |
| 功能没标 P0/P1/P2 | AI 全做 P0 → 工期爆炸 | 每条强制标优先级 |
| **AI 项目跳过 AI 三要素自检** | 痛点伪 / 数据无 / 算法做不到 → 项目暴死 | 必做三要素打分,< 3 分先 POC |
| **AI 项目没合规评估** | 上线前被法务踢出局 | 边界声明必含合规清单 |
| **跳过架构设计直接写 PRD** | AI 写出的功能拼不到一起 | 阶段 2 不可省 |
| **没二次确认就交付** | PRD 是 AI 自说自话,不是和用户对齐 | 阶段 4 不可省 |

## 10. 输出后的提示语

PRD 写完输出给用户时,**必须说这 3 句话**:

1. "这份 PRD 解决了 [N] 个 P0 + [M] 个 P1 / P2。如果 P0 范围太大,我们再砍。"
2. "验收清单需要你跑一遍才算锁定。AI 写完代码后,我们用第 5 节清单逐条勾。"
3. "如果中途有需求变更,改这份 PRD 的对应模块即可,不要散落到对话里 — 否则 AI 看不到。"
