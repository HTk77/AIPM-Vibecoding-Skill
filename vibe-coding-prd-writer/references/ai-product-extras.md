# AI 产品 PRD 必读补充

> **本文件仅 AI 项目需读。** 功能产品(无 LLM / 无生成式 / 无评测)可跳过。
> 本文件内容来自行业共识(如《AI 应用 = 传统功能产品 + AI 能力》),写 AI 产品 PRD 时务必逐条核对。

---

## 1. AI 需求三要素公式(灵魂级)

> **AI 需求 = 用户痛点 × 数据可获得性 × 算法可实现性**

三项是**乘法关系**,任一项 ≈ 0,整体 ≈ 0。这是 AI 产品立项最重要的判断框架。

### 1.1 用户痛点

| 评估问题 | 高分(8-10) | 低分(1-3) |
|---------|-----------|----------|
| 用户每天 / 每周遇到这个问题几次? | 多次 / 高频 | 偶尔 / 低频 |
| 不解决这个问题用户损失多少? | 钱 / 时间 / 机会成本明确量化 | 模糊感觉"应该有用" |
| 现有方案有多痛? | 极差 / 无方案 | 已有方案够用 |
| 用户愿意付费吗? | 已经在花钱解决 | 免费都不一定用 |

> **行业反例:** "智能客服"在中小商家是 9 分痛点(夜班无人接、损失订单),在已有 24 小时客服团队的大厂只有 3 分。**同一个产品,场景不同分数差 3 倍。**

### 1.2 数据可获得性

| 评估问题 | 高分 | 低分 |
|---------|------|------|
| 数据从哪来? | 用户自带 / 公开数据 / 已购买 | 需要去找 / 还没影子 |
| 是否独家? | 独家(护城河) | 大家都能拿到 |
| 标注成本多少? | 自动 / 用户行为埋点即得 | 需要专业人士手标 |
| 数据规模够吗? | 当前已有 1000+ 条 | 需要从 0 积累 |

> **行业案例:** 某宠物医疗 AI,创始人去小众国家买了 3000 本极稀缺专业书 + 找清华博士级人才标注,**数据壁垒让大厂都追不上**。会员一个月 ¥89 仍排队。

### 1.3 算法可实现性

| 评估问题 | 高分 | 低分 |
|---------|------|------|
| 现有 LLM 能不能做? | GPT-4 / Claude / 开源模型直接能做 | 需要训练专门模型 |
| 行业有 OK 实现吗? | 已有公司在做(可参考) | 你是第一个 |
| 评测能不能做? | 有公开评测集 | 没有评测标准 |
| 失败容忍度? | 错了用户能容忍 | 一次错就掉用户 |

### 1.4 三要素自检模板

```markdown
| 维度 | 自答 | 评分 |
|------|------|------|
| 用户痛点 | <一句话场景> | <1-10> |
| 数据可获得性 | <数据从哪来> | <1-10> |
| 算法可实现性 | <技术路线> | <1-10> |

> 任一项 < 3 → 强烈建议先 POC 不写 PRD
> 任一项 < 5 → PRD 中需在边界声明里说明该薄弱点的应对
> 三项 ≥ 7 → 直接进入 PRD 撰写
```

## 2. AI 产品评测指标体系

每个 AI 功能必须配 1-3 个评测指标。**没指标 = 没法判断 AI 是否做对了 = 项目失控**。

### 2.1 常用指标速查

| 指标 | 适用场景 | 计算方式 | 数据来源 |
|------|---------|---------|---------|
| **准确率(Accuracy)** | 分类 / 答题 / 判断 | 答对的 / 总数 | 评测集 |
| **召回率(Recall)** | RAG 检索 / 信息提取 | 找回的相关项 / 应找回的项 | 评测集 |
| **精确率(Precision)** | 推荐 / 信息提取 | 找到的对的 / 找到的总数 | 评测集 |
| **F1 分数** | 召回率 + 精确率综合 | 2×P×R / (P+R) | 评测集 |
| **响应速度** | 所有 AI 产品 | 首字节时间 / 总耗时 | 服务端打点 |
| **用户满意度** | 主观体验类 | 1-5 星打分均值 | 用户原声 |
| **稳定性** | 所有 AI 产品 | 可用率(99.X%) | 监控系统 |
| **点击率 / 转化率** | 推荐 / 内容 | 点击 / 曝光 | 行为埋点 |

### 2.2 指标 + 通过门槛

光列指标不够,必须设**通过门槛**(否则永远是"还不够好"):

```markdown
| metric | 期望值 | 当前值 | 通过门槛 |
|--------|-------|--------|---------|
| 准确率 | ≥ 85% | <填写> | 95% 通过率门槛 |
| 首字节响应 | ≤ 5s | <填写> | 90% 请求达标 |
| 满意度 | ≥ 4/5 | <填写> | 月度均值 |
```

## 3. 数据采集三渠道(行业核心方法论)

> 一个指标要想有分数,数据来自三处。**只有三条腿才稳。**

| 渠道 | 是什么 | 举例 | 何时必用 |
|------|-------|------|---------|
| **用户原声** | 用户主动打分、口述、评论 | App Store 评分、产品内反馈、满意度问卷 | 主观体验类指标 |
| **数据埋点** | 按钮上报机制,统计客观行为 | 点击次数、停留时长、转化漏斗 | 行为类指标 |
| **效果评测** | AI 专属,针对模型输出取平均分 | 准确率评测集 / Eval 打分 | AI 模型质量类 |

### 3.1 为什么三条腿都要?

- **光听用户说不行** —— 他可能说谎、情绪化、记错(满意度问卷 4 星但实际不用)
- **光看埋点不行** —— 行为不一定是用户想要的(被诱导点击 ≠ 真满意)
- **光看评测集不行** —— 评测集和真实分布有差异(过拟合)

**三个加权才是真答案。**

### 3.2 验收清单中必含

```markdown
## 5.4 数据采集三渠道(AI 项目必填)

| 渠道 | 落地方式 | 上线日 |
|------|---------|--------|
| 用户原声 | <反馈入口位置 / 评分弹窗时机> | <D-day> |
| 数据埋点 | <埋点列表 + metric 名 + 上报频率> | <D-day> |
| 效果评测 | <评测集路径 + 运行频率 + 通过率监控> | <D-day> |
```

## 4. POC 验证流程(AI 项目特有卡点)

> 行业共识:AI 项目流程比传统多 2 个卡点 —— **AI 可行性评审 + POC 验证**。
> 触发条件:三要素任一 < 3,或算法可实现性不确定。

### 4.1 POC 不是 PRD

**POC = Proof of Concept(概念验证)**,目标是用最低成本回答"这事到底能不能做"。

| 维度 | POC | PRD |
|------|-----|-----|
| 目标 | 能不能做 | 怎么做 |
| 输出 | 一个能跑的 demo + 评测结果 | 完整需求文档 |
| 范围 | 1-2 个核心场景 | 完整产品 |
| 时长 | 1-2 周 | 几周到几月 |
| 失败处理 | 改方案 / 换技术 / 砍掉 | 不允许失败 |

### 4.2 POC 模板(本 skill 选填模块 6.3)

```markdown
## POC 验证记录

| 项 | 内容 |
|----|------|
| POC 目标 | <要验证什么假设? eg: GPT-4 能不能给宠物诊断给出 90% 准确建议> |
| 数据集 | <来源 + 规模 + 怎么标注的> |
| 评测指标 | <用什么 metric 量化效果> |
| 评测结果 | <达标 X / 未达标 Y + 具体数字> |
| 是否进入 PRD | <是 / 否 / 暂缓 + 原因> |
| 暂缓的复活条件 | <eg: 等 GPT-5 发布 / 数据集扩大到 1 万条 / 价格降至 $0.01/req> |
```

### 4.3 行业流程图

**传统产品需求流程:**
```
需求采集 → 待讨论 → 需求讨论会 → 通过 → 打包 → 评审 → 开发 → 发布
```

**AI 产品需求流程(多 2 个卡点):**
```
需求采集 → 待讨论 → 需求讨论会 → 通过
   → [ AI 可行性评审 ]                  ← 新增卡点 1
      ├── 技术难度高 → 拒绝
      ├── 质量差 / 成本高 → 暂缓(等新模型 / 降价)
      └── 通过 → POC 验证                ← 新增卡点 2
                ├── 失败 → 暂缓
                └── 成功 → 写 PRD → 评审 → 开发 → 发布
```

> **暂缓的复活条件**:新模型发布、调用价格降下去、POC 效果提升 —— 都可以让一个暂缓的需求复活。

## 5. 合规 / 法务风险清单(AI 项目必查)

> **行业警示:** 某项目花两三个月做 B 站智能封面生成,上线前一周被法务约谈砍掉。**合规必须前置,不能等到上线前才补。**

### 5.1 高频风险类别

| 风险 | 触发场景 | 应对方案 |
|------|---------|---------|
| **数据隐私** | 用户输入存哪、存多久、是否加密、是否给第三方 | 隐私政策 + 加密存储 + 用户可删除 |
| **内容合规** | LLM 生成内容可能违规(色情 / 暴力 / 政治 / 谣言) | 输出前过滤 + 用户举报机制 + 黑名单 |
| **版权** | 训练 / 使用素材的权利,生成内容的版权归属 | 数据来源审查 + 用户协议明示 |
| **算法偏见** | 对某类用户(性别 / 种族 / 年龄)产出有偏 | 评测集多样化 + 偏见检测 |
| **行业监管** | 医疗 / 金融 / 教育 / 法律等强监管行业 | 资质前置 + 法务过审 + 牌照 |
| **跨境数据** | 涉及海外用户 / 数据出境 | 当地法务 + 数据本地化 |
| **未成年人** | 用户可能含未成年 | 实名 + 内容分级 + 限时 |

### 5.2 边界声明中必填

```markdown
### 3.4 合规 / 法务风险评估(AI 项目)

| 风险类别 | 是否相关 | 应对方案 | 法务前置 ✓ |
|---------|---------|---------|----------|
| 数据隐私 | 是/否 | <方案> | <已确认/待沟通> |
| 内容合规 | 是/否 | <方案> | <已确认/待沟通> |
| 版权 | 是/否 | <方案> | <已确认/待沟通> |
| 算法偏见 | 是/否 | <方案> | <已确认/待沟通> |
| 行业监管 | 是/否 | <方案> | <已确认/待沟通> |
```

### 5.3 谁来评估

- 大公司:法务部门 / 合规专员 / 风控
- 小公司 / 个人:律师朋友咨询 / 行业从业者经验 / 政策原文阅读

**Vibe coding 自用产品也别忽视!** 即使自用,如果产品涉及外部数据(爬取 / 抓取 / 集成),仍可能违反第三方协议。

## 6. AI 产品技术可行性的特殊维度

PRD 模块 4 设计技术契约里,AI 项目要补这些评估:

### 6.1 数据质量

```markdown
| 维度 | 评估 |
|------|------|
| 脏数据率 | <估计 X%> |
| 标注成本 | <每条 $X / 人,总 $Y> |
| 训练集规模 | <当前 X 条,需要 Y 条> |
| 数据时效 | <更新频率 / 是否过时> |
```

### 6.2 算力与延迟

| 维度 | 关键问题 |
|------|---------|
| **部署位置** | 端侧(本地) / 云端(API) / 混合 |
| **单次延迟** | 实时(< 1s) / 准实时(< 5s) / 异步 |
| **并发能力** | 每秒多少请求 / 高峰承载 |
| **成本预算** | 单次成本 + 月度上限 + 突发预案 |

### 6.3 端侧 vs 云端的判断

| 选端侧 | 选云端 |
|-------|-------|
| 离线场景(无人机救援 / 偏远地区) | 联网稳定场景 |
| 隐私敏感(医疗 / 律师对话) | 普通业务 |
| 实时性要求高(自动驾驶) | 容忍秒级延迟 |
| 单点不需重型模型 | 通用大模型能力 |

> **行业洞察:** 端侧部署的小模型不必追求 Cloud 级通用能力,**单项能力够用就行**(无人机救援只需识别人形)。
