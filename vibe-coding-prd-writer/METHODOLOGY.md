# 方法论与设计来源

> 本文件解释这个 skill 的**来历、参考、设计选择、边界**。
> 不是给 AI 看的指令(那是 SKILL.md 的工作),是给你和未来其他 PM 看的"为什么"。

---

## 1. 来源:这个 skill 怎么诞生的

### 1.1 实战起点

2026-05-03 — 4 日,赫庭从 0 启动一个 AI 产品(「赫庭的 AI 圆桌会议」)。在用 Claude Code 协作完成产品 + PRD + 原型 + Agent prompt 工程的 10 小时里,反复体验到 vibe coding 与传统开发的 5 个核心差异:

| 维度 | 传统开发流程 | Vibe Coding 流程 |
|------|------------|----------------|
| PRD 读者 | 开发团队 | AI 编程工具 |
| 模糊度 | 可模糊,人会推理补全 | 必须精确,模糊 = 模糊代码 |
| 验收 | 后置文档 | 每个功能内嵌 |
| 边界 | 隐含 | 显式声明 |
| 迭代 | 需求→评审→开发分阶段 | 用户↔AI 实时协作 |

实战中发现**没有现成 skill 把这些差异工程化**,于是沉淀了本 skill。

### 1.2 行业方法论补强

实战经验只是骨架,血肉来自系统化的产品需求方法论。本 skill 大量参考了这份课程笔记:

> 📚 **核心参考:** 「从原型图到 PRD:AI 产品需求全生命周期系统笔记」(2026-04-23 课程,本机存放路径见 `~/Library/.../系统笔记整理/`)

具体借鉴的概念:

|-----------|-----------------|
| AI 需求三要素公式(用户痛点 × 数据可获得性 × 算法可实现性) | §3.1 项目级 + §3.2 功能级双层自检 |
| 用户故事标准句式("作为...我想要...以便...") | §3.2 功能契约必填字段 |
| 数据采集三渠道(原声 / 埋点 / 评测) | references/ai-product-extras.md §3 + 验收清单 §5.4 |

### 1.3 与原始课程的边界

本 skill **不复制**课程笔记的全文内容,只**提取与 vibe coding PRD 直接相关**的部分。课程笔记完整覆盖了:
- 需求收集(用户访谈 / 问卷 / 可用性测试 / AB)
- 需求分析(六步三段)
- 文档四件套(BRD / MRD / PRD / TRD)

本 skill 只做 **PRD 这一份**,且只做 vibe coding 场景的 PRD。其他 4 件套和需求收集分析,有专门的上游 skill(已有的 `BRD-MRD-竞品地图生成` / `competitive-analysis`)。

## 2. 设计哲学(为什么这样设计)

### 2.1 为什么需要 4 阶段流程 + 3 次用户确认

**反直觉的洞察:** PRD 写得好不好,80% 取决于**写之前**做了什么,不是写本身。

赫庭项目实战中的真实痛点:
- 拿到模糊想法直接开写 → PRD 重写 4 次
- 写完没二次确认 → AI 写代码时按文档表面意思理解,做出来不是想要的

→ 引出 4 阶段:输入对齐 / 架构设计 / PRD 撰写 / 二次确认。
→ 引出 3 次确认 ✋ #1 #2 #3 作为强制停顿点。

**关键:** 这 3 次确认不是流程仪式,是**把 AI 自说自话变成与用户对齐**的核心机制。

### 2.2 为什么 5 必写模块,而不是 8 或 12

参考了课程笔记的需求采集卡(7 字段)和需求分析六步,综合后归纳出**写给 AI 必须有 + 缺一不可**的 5 项:

| 必写模块 | 回答的核心问题 | 不写的代价 |
|---------|--------------|----------|
| 项目身份卡 | 这是个什么东西? | AI 抽风 |
| 功能契约 | 做哪些事 + 怎么算做对了? | 验收无据 |
| 边界声明 | 不做哪些事 + 失败兜底? | scope creep + 隐性 bug |
| 设计技术契约 | 用什么栈 + 长什么样? | AI 自选偏好 |
| 验收清单 | 整体怎么验? | "做完了"不可证 |

更多的字段(用户故事 / 用例 / 状态图等)放选填 — 不是不重要,是不强制。

### 2.3 为什么 AI 项目要和功能产品分支

行业共识:**AI 应用 = 传统功能产品 + AI 能力**。但 AI 能力部分有 5 项功能产品没有的考量:

1. 数据可获得性(数据壁垒)
2. 算法可实现性(技术天花板)
3. 评测体系(模型质量度量)
4. 合规风险(内容 / 版权 / 偏见)
5. 算力延迟(端侧 vs 云端)

不显式分支处理,AI 项目 PRD 要么漏关键内容,要么把功能产品当 AI 项目过度设计。

### 2.4 为什么触发词要"智能识别"而非"广撒网"

赫庭的同事也是 PM,日常工作里也会说"写 PRD"、"撰写需求文档"。如果本 skill 触发词太广,会污染他们的传统工作流,反而让 skill 名声变臭。

→ 设计为三档:**明确触发 / 模糊触发先反问 / 严禁触发**。

这是对其他 PM 同事的尊重 — skill 不应该闯入它不该管的领域。

## 3. 边界:本 skill 不做什么

| 不做 | 理由 |
|------|------|
| 需求挖掘 / 用户访谈 | 这是上游(用户研究阶段),需要面对面、问卷、观察 — 不是 skill 能做的 |
| 竞品调研 / 市场分析 | 已有 `competitive-analysis` skill |
| 写 BRD / MRD / TRD | 已有 `BRD-MRD-竞品地图生成` skill |
| 视觉原型 / Figma 设计 | 设计是另一个专业领域,本 skill 只链接到原型源码 |
| Agent prompt 工程 | 等 `vibe-coding-prompt-engineer` skill 沉淀,本 skill 在 §4 选填仅做引用 |
| 给开发团队评审的传统 PRD | 不是本 skill 的目标场景 |
| 项目落地 / 写代码 | 本 skill 输出后,交给 Claude Code / Cursor 等 AI 编程工具执行 |
| 写完 PRD 后的 task 拆解 | 那是 vibe-project-init 或下游 skill 的职责 |

## 4. 优化路径(skill 怎么变得越来越好)

### 4.1 v0.2.0 → v0.3.0(实战验证期)

**触发条件:** 跑过 3-5 个不同行业项目后

**优化方法:**
- 收集"skill 没起作用"的 case,补到 checklist 反例
- 观察用户实际触发表达,扩展或收窄触发词
- 当某个模块被反复改动时,可能说明该模块的字段需要简化

### 4.2 v0.3.0 → v1.0.0(团队推广期)

**触发条件:** 你自己稳了,想给同事用

**优化方法:**
- 写一份 SHARING-GUIDE.md 教其他 PM 怎么用
- 收集同事的 false positive / false negative
- 加多端 checklist(iOS / 小程序 / Android 上线特有项)
- 与上下游 skill 串成 skill 链(vibe-project-init → 本 skill → vibe-coding-prompt-engineer)

### 4.3 永不优化的部分

有些事情应该保持稳定,频繁动会破坏 skill 的可预测性:

- 5 必写模块的命名和顺序(身份 → 功能 → 边界 → 设计技术 → 验收)
- 4 阶段流程的骨架(输入对齐 → 架构 → 撰写 → 二次确认)
- 写作铁律 1-6(可勾选 / 可观测 / 必有验收 / 边界显式 / 决策可追溯 / 字不如表)
- AI 三要素公式

变的是细节,不变的是骨架。

## 5. 本 skill 给其他 skill 的启示(沉淀的元方法)

如果你后续要沉淀其他 vibe coding 方法论 skill(比如 `vibe-project-init`、`vibe-coding-doc-auditor`、`engineering-control-review`),本 skill 的 4 个设计选择值得复用:

1. **流程优先于内容** — 先定流程框架(几阶段 + 几次用户确认),再填内容
2. **触发词分三档** — 明确 / 模糊 / 严禁,避免污染同事日常工作
3. **示例用模板 + 微示例,不用完整案例** — 完整案例会让下次跨行业输出"看着像上次的项目"
4. **wrapping 层独立于 skill 主体** — README / CHANGELOG / METHODOLOGY 在主目录,SKILL.md 单独是 AI 入口,references/ 装详细参考。这样人和 AI 的视角分离。
